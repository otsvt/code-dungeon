# Промпт на архитектурный рефакторинг Code Dungeon

## Назначение

Этот документ — рабочая инструкция для последовательного рефакторинга существующего проекта. Его нужно применять к реальному коду репозитория, а не использовать как повод переписать приложение с нуля.

Основная цель: отделить игровой контент, доменные правила, состояние приложения и отображение так, чтобы вопросы сначала читались из локальных JSON-файлов, а позже могли приходить с backend без переписывания React UI, Phaser-сцен и правил прохождения комнат.

## Роль

Ты — senior frontend/gameplay architect, работающий с Next.js, React, Phaser, Zustand и TypeScript.

Проводи рефакторинг по принципам SOLID и в направлении Feature-Sliced Design, но без формального дробления каждого файла и без создания слоёв, которые пока не решают реальную задачу.

## Обязательный контекст проекта

- `Phaser` отвечает за игровую сцену, игровые объекты, переходы и анимации.
- `React` отвечает за HUD, overlay и обычный интерфейс.
- `Zustand` хранит состояние, но не должен быть источником контента или содержать доменные алгоритмы.
- `src/game` сейчас содержит доменные типы, правила комнат, генерацию маршрута, эффекты и stores.
- `src/app/[locale]/game` сейчас содержит Phaser-сцены, Phaser-entities и React UI игрового экрана.
- Вопросы сейчас находятся в TypeScript:
  - `src/game/content/questions/battleQuestions.ts`;
  - `src/game/content/questions/hrQuestions.ts`.
- Выбор вопросов и расчёт результата сейчас находятся в:
  - `src/game/challenges/challenge.ts`;
  - `src/game/rooms/hrRoom.ts`.
- Создание активного challenge сейчас выполняет `src/game/store/useGameUiStore.ts`.
- Применение результата комнаты выполняет `src/game/store/useGameRunStore.tsx`.
- Реальный код имеет приоритет над старыми архитектурными документами.

## Главные архитектурные правила

### 1. Контент не является логикой

- Тексты вопросов, варианты ответов, правильные ответы, кодовые примеры, принадлежность к технологии и вид вопроса хранятся только в JSON.
- В `.ts`, `.tsx`, Phaser-сценах и Zustand stores не должно быть текстов вопросов и вариантов ответов.
- Нельзя генерировать или дописывать пользовательский текст вопроса TypeScript-функциями вроде `overflowQuestion`.
- Длинная версия текста тоже должна полностью находиться в JSON.

### 2. Источник вопросов заменяемый

Потребитель зависит не от JSON и не от будущего HTTP API, а от порта:

```ts
interface QuestionRepository {
  getBattleQuestions(
    technologyId: TechnologyId,
    count: number,
  ): Promise<ChallengeQuestion[]>;

  getHrQuestions(): Promise<ChallengeQuestion[]>;
}
```

Точная сигнатура может быть скорректирована после проверки вызывающего кода, но смысл границы сохраняется:

- локальный JSON — первая реализация репозитория;
- backend API — будущая реализация того же контракта;
- UI, stores, Phaser и доменные правила не знают, откуда пришли вопросы.

Если асинхронный контракт на первом шаге слишком сильно ломает текущий синхронный игровой flow, допускается временный синхронный порт. Это решение должно быть явно помечено как переходное, а структура DTO и mapper уже должна быть пригодна для HTTP.

### 3. Внешние данные нельзя считать доменной моделью

JSON и будущий ответ backend — это DTO, а не `ChallengeQuestion`.

На границе источника должны находиться:

- проверка структуры данных;
- проверка уникальности `id`;
- проверка наличия вариантов;
- проверка, что `correctOptionId` существует среди `options`;
- проверка поддерживаемых локалей;
- проверка `technologyId` для battle-вопросов;
- преобразование DTO в доменную модель;
- понятная ошибка при невалидном контенте.

Не маскировать ошибки небезопасным `as ChallengeQuestion[]`.

На первом этапе не добавлять библиотеку схем только ради нескольких JSON-файлов. Сначала оценить, достаточно ли небольшого валидатора/type guard. Если контракт разрастается, отдельно предложить Zod или аналог и объяснить пользу.

### 4. Доменная логика остаётся чистой

Чистые функции должны отвечать за:

- выбор подходящих вопросов из уже загруженного набора;
- расчёт battle outcome;
- расчёт HR outcome с учётом impression и допустимых ошибок;
- выбор награды;
- правила последовательности комнат.

Они не должны:

- импортировать JSON;
- обращаться к Zustand;
- обращаться к React или Phaser;
- выполнять HTTP-запросы;
- изменять переданные объекты.

### 5. Store координирует состояние, но не владеет правилами

Zustand action может:

- вызвать use case;
- сохранить полученный challenge;
- принять завершение challenge;
- сохранить результат.

Zustand action не должен:

- фильтровать контент;
- валидировать JSON;
- рассчитывать правила прохождения;
- выбирать награды;
- содержать строки контента;
- напрямую импортировать конкретный JSON-файл.

### 6. UI только отображает и сообщает действия

`ChallengeOverlay` получает готовую view model:

- локализованный prompt;
- локализованные labels;
- прогресс;
- разрешённое количество ошибок;
- необходимые asset references.

Компонент не должен знать:

- где хранится JSON;
- как определяется HR/battle outcome;
- как выбирается награда;
- как устроен backend DTO.

### 7. Phaser не управляет вопросами

Phaser-сцена может:

- определить факт входа в комнату;
- запустить соответствующий application action;
- ждать результат;
- проиграть визуальную реакцию;
- продолжить переход.

Phaser-сцена не должна:

- содержать вопросы и ответы;
- читать JSON;
- рассчитывать правильность ответов;
- повторно создавать награду, если она уже создаётся application/domain слоем;
- дублировать правила завершения комнаты.

## Целевая структура без избыточного FSD

Это ориентир, а не приказ механически создать все папки:

```text
src/
  app/
    [locale]/game/
      scenes/                    # Phaser composition
      entities/                  # Phaser game objects
      ui/                        # композиция игрового экрана

  entities/
    challenge/
      model/                     # доменные типы challenge
      ui/                        # переиспользуемое отображение вопроса при необходимости
    technology/
    effect/

  features/
    play-challenge/
      model/                     # состояние прохождения текущего challenge
      ui/                        # ChallengeOverlay
    enter-room/
      model/                     # orchestration входа и завершения комнаты, если оправдано

  game/
    domain/
      challenge/                 # чистые правила результата
      room/                      # чистые правила комнат и наград
      run/                       # чистые правила забега
    application/
      challenge/                 # use cases запуска/завершения challenge
      room/                      # use cases завершения комнаты
    infrastructure/
      questions/
        data/
          battle-questions.json
          hr-questions.json
        dto/
        mappers/
        localQuestionRepository.ts
        questionRepository.ts
    store/                       # Zustand adapters/application state

  shared/
    i18n/
    ui/
    assets/
```

Не переносить файлы ради совпадения с этой схемой. Перемещение разрешено, только если после него становится яснее направление зависимостей или устраняется существующее смешение ответственности.

## Формат локального JSON

На первом шаге использовать два файла:

```text
src/game/infrastructure/questions/data/battle-questions.json
src/game/infrastructure/questions/data/hr-questions.json
```

Рекомендуемый battle DTO:

```json
{
  "version": 1,
  "questions": [
    {
      "id": "html-semantic-main",
      "kind": "battle",
      "technologyId": "html",
      "prompt": {
        "ru": "Текст вопроса",
        "en": "Question text"
      },
      "code": null,
      "options": [
        {
          "id": "a",
          "label": {
            "ru": "Вариант",
            "en": "Option"
          }
        }
      ],
      "correctOptionId": "a"
    }
  ]
}
```

HR DTO использует тот же базовый контракт, но:

- `kind` равен `hr`;
- `technologyId` отсутствует;
- HR-правила impression и допустимых ошибок не хранятся в вопросах.

`version` нужен для будущей миграции backend-контракта. Не добавлять заранее pagination, timestamps, database ids и другие поля, которые сейчас не используются.

## Направление зависимостей

Разрешённое направление:

```text
JSON / future HTTP response
        ↓
DTO validation + mapper
        ↓
QuestionRepository
        ↓
application use case
        ↓
Zustand adapter
        ↓
React UI / Phaser orchestration
```

Доменные правила могут использовать доменные типы, но ничего не знают о JSON, HTTP, Zustand, React и Phaser.

Запрещены обратные импорты из domain/application в `app`, React UI, Phaser или конкретную infrastructure-реализацию.

## Применение SOLID к этому проекту

- **SRP:** контент, валидация DTO, выбор вопросов, расчёт outcome, управление состоянием и отображение находятся в разных ответственных модулях.
- **OCP:** подключение API-репозитория не требует менять UI и доменные правила.
- **LSP:** local и HTTP реализации `QuestionRepository` возвращают одинаковую валидную доменную модель и одинаково сообщают об ошибках.
- **ISP:** не создавать один огромный `GameService`; use cases и порты должны быть узкими.
- **DIP:** application слой зависит от интерфейса репозитория, а не от JSON import или `fetch`.

## Антипаттерны, запрещённые в ходе рефакторинга

- Хардкод вопросов или вариантов в `.ts`, `.tsx`, сценах и stores.
- Импорт JSON непосредственно из UI, store или Phaser-сцены.
- `as ChallengeQuestion[]` вместо проверки внешних данных.
- God-store, в котором одновременно находятся content loading, правила, навигация и UI state.
- Универсальный `utils.ts`, куда складывается несвязанная логика.
- Циклические импорты через barrel-файлы.
- Создание интерфейса на каждую функцию «ради SOLID».
- Формальная раскладка по FSD, после которой связанные файлы сложнее найти.
- Одновременная смена структуры, поведения, текстов и дизайна в одном шаге.
- Переписывание рабочего Phaser/React flow без теста, доказывающего необходимость.
- Сохранение случайного результата отдельно в Phaser и отдельно в store.

## Порядок рефакторинга

### Этап 1. Зафиксировать текущее поведение

- [ ] Проверить актуальные battle и HR сценарии по коду.
- [ ] Зафиксировать тестами выбор вопросов, outcome, allowed mistakes и награды.
- [ ] Зафиксировать отсутствие перехода HR → HR.
- [ ] Не менять игровое поведение.

Критерий готовности: существующие сценарии описаны тестами, текущий test suite зелёный.

### Этап 2. Перенести вопросы в JSON и закрыть границу данных

- [ ] Создать versioned JSON DTO для battle-вопросов.
- [ ] Создать versioned JSON DTO для HR-вопросов.
- [ ] Перенести тексты без генерации строк в TypeScript.
- [ ] Удалить `battleQuestions.ts`, `hrQuestions.ts` и `overflowQuestion` после переключения потребителей.
- [ ] Сохранить существующие `id`, правильные ответы, локали и кодовые примеры.
- [ ] Исправить обнаруженную повреждённую кодировку контента, если она подтверждается чтением файла как UTF-8 и отображением в приложении.
- [ ] Описать JSON DTO отдельно от доменной модели.
- [ ] Провалидировать version и структуру каждого вопроса.
- [ ] Проверить ссылочную целостность `correctOptionId`.
- [ ] Преобразовать DTO в неизменяемую доменную модель.
- [ ] Добавить unit tests на валидный и невалидный контент.

Критерий готовности: поиск по `src/**/*.ts(x)` не находит тексты и варианты вопросов; UI показывает тот же контент из JSON; повреждённый JSON приводит к контролируемой понятной ошибке, а не к падению внутри UI.

### Этап 3. Ввести QuestionRepository

- [ ] Объявить порт источника вопросов.
- [ ] Реализовать local JSON adapter.
- [ ] Перевести use case запуска challenge на порт.
- [ ] Не импортировать local adapter из domain.
- [ ] Определить composition root, где concrete repository передаётся приложению.

Критерий готовности: local repository можно заменить test double без Zustand, React и Phaser.

### Этап 4. Отделить application flow от Zustand

- [ ] Вынести запуск battle challenge в use case.
- [ ] Вынести запуск HR challenge в use case.
- [ ] Вынести завершение challenge и подготовку результата комнаты в use case.
- [ ] Оставить store тонким адаптером состояния.
- [ ] Устранить повторный расчёт награды между сценой и store.

Критерий готовности: application flow тестируется без React hook и без запуска Phaser.

### Этап 5. Уточнить границу React/Phaser

- [ ] Оставить сцене только вход в комнату, визуальный lifecycle и ожидание результата.
- [ ] Передавать overlay готовую view model.
- [ ] Убрать из overlay доменные вычисления, если они там остались.
- [ ] Убедиться, что закрытие overlay и завершение комнаты идемпотентны.

Критерий готовности: один результат challenge применяется ровно один раз, а сцена не знает структуру источника вопросов.

### Этап 6. Умеренно выровнять структуру

- [ ] Переместить только те модули, для которых уже сформировалась понятная граница.
- [ ] Удалить временные re-export и старые пути.
- [ ] Проверить отсутствие циклических импортов.
- [ ] Обновить актуальную документацию проекта.

Критерий готовности: структура отражает реальные ответственности, но не содержит пустых или одноразовых архитектурных слоёв.

## Правила выполнения каждого этапа

Перед изменениями:

1. Прочитать связанные реальные файлы.
2. Показать один конкретный следующий шаг и список затрагиваемых файлов.
3. Назвать сохраняемые поведенческие инварианты.
4. Не начинать следующий этап без подтверждения текущего.

Во время изменений:

1. Делать минимальный связный diff.
2. Не смешивать рефакторинг с изменением геймдизайна.
3. Не форматировать и не переписывать несвязанные пользовательские изменения.
4. Сначала добавлять новый путь, переключать потребителей, затем удалять старый.
5. После каждого смыслового шага запускать пропорциональные проверки.

После изменений:

1. Показать изменённые файлы.
2. Кратко объяснить новое направление зависимостей.
3. Запустить TypeScript, ESLint, unit tests и production build.
4. Отдельно сообщить, если проверка не запускалась или упала.
5. Показать checklist текущего этапа и остановиться для подтверждения.

## Общие критерии завершения рефакторинга

- [ ] Все battle и HR вопросы находятся в JSON.
- [ ] В TypeScript нет генераторов контентных строк.
- [ ] JSON проходит validation и mapping на границе infrastructure.
- [ ] Источник вопросов скрыт за `QuestionRepository`.
- [ ] Замена local JSON adapter на HTTP adapter не затрагивает UI, Phaser и domain.
- [ ] Domain не импортирует infrastructure, React, Phaser и Zustand.
- [ ] Stores не содержат контент и сложные игровые правила.
- [ ] React overlay не рассчитывает доменный outcome.
- [ ] Phaser не читает вопросы и не дублирует выдачу наград.
- [ ] HR и обычные battle эффекты остаются разделены.
- [ ] После HR нельзя сразу получить следующую HR-комнату.
- [ ] Правила ошибок HR сохраняются: плохое впечатление — 0, обычное — 1, хорошее — 2.
- [ ] TypeScript, ESLint, unit tests и production build проходят.

## Первый предлагаемый шаг после подтверждения

Выполнить только этап 2: перенести battle и HR вопросы в два versioned JSON-файла, добавить локальный loader с DTO validation и mapper, затем переключить текущие функции получения вопросов на него.

На этом шаге:

- не переносить stores;
- не менять Phaser-сцены;
- не менять UI;
- не вводить HTTP;
- не менять правила исходов и наград;
- не менять тексты и количество вопросов, кроме подтверждённого исправления кодировки.

После прохождения тестов остановиться и показать результат перед началом следующего архитектурного шага.
